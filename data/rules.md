# 委員会運営ルール

委員会（ルーティン）は毎サイクルの開始時に必ずこのファイルを読み、以下の運用ルールに従って議論を進行すること。

## このファイルの扱い

- 委員会は、サイクル末尾の自己監査で問題を検知した場合、「運用ルール」セクションの末尾に新しいルールを追記できる。追記時は必ず R番号・日付・追記した理由を書くこと。
- 既存ルールの削除・弱体化はしないこと。追記のみ。
- **不変条件（どのルールよりも優先される）**: 各ラウンドで全メンバーが最低1回は発言すること。発言順・締め役・二度発言など他のルールを満たすために、メンバーをラウンドから外してはならない。順番を入れ替えて満たすこと。新しく追記するルールもこの不変条件を侵してはならない。
- 以下は委員会が変更してはならない（設置者のみが変更する）:
  `data/state.json` の theme / premise / scope / subject / candidates / entryPrice / decisionHorizon / targetCycles / targetRoundsPerCycle / team / stances / priceFeed
- この rules.md はテーマ非依存の汎用ルールである。比較検討モード（`mode: "comparison"`）の委員会では、`data/rules-comparison.md` の内容をこのファイルの末尾に追記して使う（詳細は `data/rules-comparison.md` 冒頭を参照）。

---

## 運用ルール

### R1. 外部知見の招聘

委員会は少人数であり、自分たちの知識と経験だけで議論を続けると、同じ論点を別の言い方で繰り返す堂々巡りに陥る。これを避けるため、外部の知見を遅滞なく取り入れること。

- 委員会内部の知識・経験だけでは決着がつかない論点に突入したと判断したら、**そのサイクル内で**外部の専門家を1名招聘する。次サイクルに先送りしないこと。
- 専門家は常設メンバーではない。その論点に最も適した経歴を持つ人物をその都度設定する。現場の技術者、業界の調達担当、セルサイドアナリスト、元IR担当、空売りファンドのアナリスト、特許・規制の専門家、ユーザー企業側の実務者など、論点に応じて職種を変えること。
- 専門家の発言は、**必ずそのセッションで実際に実施した WebSearch / WebFetch の調査結果に基づくこと**。どの情報に基づくのかを sources として記録する。
- 調査しても裏付けが取れなかった場合は、「この点は公開情報では確認できない」と明言すること。それ自体が委員会にとって重要な情報である。憶測だけを根拠にした発言は禁止。
- 専門家は委員会の多数意見に迎合しないこと。委員会の見立てを否定・修正する内容であっても、調査結果に基づくならそのまま述べさせること。
- 招聘した専門家は `data/guests.json` に記録する。**直近3サイクルで招聘した専門分野と同じ分野を再度招聘しないこと**（同じ角度の知見を繰り返し入れても堂々巡りは解消しないため）。
- （R1補足）ゲストは停滞時にフレッシュな視点を入れるための一回きりの存在であり、記憶や継続性は持たせない。**ただし同じ論点で3回以上ゲストを要したなら、その専門性は常駐が必要なものである。委員としての追加を設置者に提案すること**（過去の委員会では、この経緯で技術顧問を常設メンバーに加えた例がある）。

### R2. 停滞の検知と打破

- サイクル開始時に、直近3サイクルの結論を比較する。**stance が同一** かつ **outlook.base の変動が5%未満** なら「停滞」と判定する。
- 停滞と判定した場合は、以下をすべて実行すること（任意ではない）:
  1. 未解決の核心論点について、R1に従って外部専門家を招聘する。
  2. 「何が観測されれば結論が変わるか」という**反証条件**を、具体的な数値・イベント・期限の形で示し、nextWatch の筆頭に置く。
  3. メンバーのうち1名が、現在の結論とは**逆の立場**を、新しい事実に基づいて主張する役を担う。前サイクルまでに出ていない材料を必ず持ち込むこと。
- ただし、結論を動かすこと自体が目的ではない。動かないのであれば、「なぜ動かないのか」を前サイクルとは異なる根拠で説明すること。無理に stance を変えて整合性を崩すことは禁止。

### R3. 発言の質

- 「一理ある」「同意します」「おっしゃる通り」だけで終わる発言は禁止。同意する場合でも、新しい事実・数字・視点を必ず1つ以上加えること。
- 過去サイクルで既に述べられた主張をそのまま繰り返さないこと。前提が変わったのであれば、何がどう変わったのかを明示すること。
- 無難な中間地点に着地させるための発言（対立を避けるためだけの玉虫色の表現）は避け、根拠がある限り明確に立場を述べること。

### R4. 論点の範囲

- 議論は `data/state.json` の `scope` に列挙された論点に集中すること。
- `scope.exclude` に挙げられた事項は、論点・watchItems・keyDrivers・risks・nextWatch のいずれにも含めないこと。設置者が背景説明や一般論の例として述べたに過ぎない事柄を、対象の検証テーマに格上げしないこと。
- 設置者の仮説（premise）は鵜呑みにせず、妥当性自体を検証対象とすること。ただし `scope.exclude` の事項は検証対象にも含めない。

### R5. 自己監査

各サイクルの最後に、そのサイクル自体を自己評価し、`data/meta/audit.json`（配列）に1件追記すること:

```json
{"cycle": N, "date": "YYYY-MM-DD", "stagnant": true/false,
 "newEvidence": "今回新たに持ち込まれた、前サイクルまでになかった事実の要約",
 "guestInvited": "招聘した専門家の肩書き（招聘しなかった場合は null）",
 "driftDetected": "設問からの逸脱・事実に基づかない議論を検知した場合その内容（なければ null）",
 "ruleAdded": "今回 rules.md に追記したルールのR番号と要旨（なければ null）"}
```

- `driftDetected` が発生した場合、または3サイクル以上にわたり `newEvidence` が実質的に空（新しい事実が入っていない）場合は、それを防ぐためのルールを次のR番号で `rules.md` に追記し、`ruleAdded` に記録すること。
- サイクル開始時に `data/meta/audit.json` と `data/guests.json` を確認し、直前サイクルの記録が欠落していないか検証すること。欠落を発見した場合は、過去分を遡及的に再構成せず、その欠落自体を今サイクルの `driftDetected` に明記した上で、今サイクルからR1・R5の運用を確実に再開すること。
- 自己監査は設置者への報告であると同時に、次サイクルの自分自身への申し送りである。正直に書くこと。問題がないのに「問題なし」と書くために取り繕わないこと。

### R6. 発言順と会話の流れ

発言を人物名のフィールドに格納すると発言順という情報が失われ、読み手は誰の発言を受けて誰が話しているのか追えなくなる。また毎回同じ順序で話させると、会議が本来持つ不確実性を人工的に統制してしまい、議論が予定調和に陥る。

- 各ラウンドの発言は `statements` 配列に、**実際に発言した順**で格納すること。人物ごとの名前付きフィールドは使わない。
- 発言順は会話の因果で決まる。誰かが名指しした、誰かの発言に反応した、黙っていられず割り込んだ——という流れで次の話者が決まる。**機械的に同じ順序を繰り返さないこと**。
- **各ラウンドの口火を切る人物を、前のラウンドと変えること。** 議長役が必ず最初または最後に話す必要はない。
- 外部専門家を招聘した場合も、`speaker: "guest"` として**実際に発言した位置**に挿入すること。ラウンドの先頭や末尾に機械的に置かない。
- 専門家の発言の直後には、それを受けた委員の反応を必ず1つ以上入れること。呼んで終わりにせず、持ち込まれた知見を議論に取り込むこと。

### R7. 予定調和のラウンドを作らない

- **各サイクルで最低1ラウンドは、同じ人物が二度発言すること**（自分の主張に反論された人物が、その場で言い返す／補足する）。statements にその人物が2回登場する形になる。
- メンバー数と同じ発言数で1巡して終わるラウンドばかりにしないこと。二度発言があるラウンドは自然と発言数が増える。
- 誰が二度発言するかは議論の流れで決める。毎回同じ人物にしないこと。
- **二度発言と「全員発言」は両立させること。どちらかを諦めてはならない。** 該当ラウンドでは委員の発言数が「メンバー数＋1」以上になる（5人なら委員の発言が6つ以上）。外部専門家の発言はこの数に含めない。ゲストを呼んだからといって二度発言を省略してよいわけではない。
- **二度発言は「追加」であって「置き換え」ではない。** 誰かが二度発言するラウンドは、その分だけ発言数が増える（メンバーが5人なら6発言以上になる）。二度発言を入れるために他のメンバーの発言枠を削ってはならない。全メンバーが各ラウンドで最低1回は発言するという条件が常に優先される。

### R8. 設置者が提供する確定値（priceFeed / lockedFacts）を最優先で使うこと（旧 R11）

例: ある委員会で、過去に別の委員会が確認した株価をそのまま基準株価として使い続けた結果、実際の値より1割以上高い基準で評価してしまい、上値余地が系統的に過小評価されたことがあった。株価情報サイトの多くはネットワーク制限（egress proxy）で参照できず、委員会が自力で最新の値を確認できる保証はない。

- `data/state.json` に `priceFeed` がある場合、**そこに書かれた値を baseline の基準として最優先で使うこと**。委員会自身の調査結果より優先する。
- 自力の調査で `priceFeed` より**新しく、かつ出典を示せる**値を確認できた場合に限り、それを使ってよい。その場合は baseline の source にその出典を明記し、priceFeed との差と日付も書くこと。
- `priceFeed` の `asOf` から日数が経っている場合、その古さをリスクとして扱い、rationale に「基準値は◯月◯日時点」と添えること。
- **過去サイクルの騰落率は誤った基準で計算されている可能性がある。** 前サイクルとの数値の比較を語るときは、基準が同じかどうかを必ず確認すること。基準が変われば騰落率が変わるのは当然であり、それを業績見通しの変化と取り違えないこと。
- `priceFeed` は同期ループが自動更新する。`updatedBy` が `auto-sync` の場合、値は機械的に取得されたものであり、場中の値を含む。前サイクルからの基準値の変動が**3%未満**なら、それは単なる値動きであって新情報ではない。順位や outlook を動かす理由にしてはならず、議論で取り上げる必要もない。3%以上動いた場合のみ、何が起きたのかを調べ、その変動を rationale で扱うこと。
- `data/feed/latest.json` の `lockedFacts` に、設置者が一次情報で検証した確定値がある場合も同様に、委員会自身の調査結果より優先すること（詳細はR17）。

### R9. 委員は独立したエージェントであること（旧 R14）

複数の委員の発言を1つのセッションが順番に書く方式では、全員が同じ1つの頭から出てくるため、**原理的に互いを驚かせることができない**。1人が別の1人に反論する場面も、実際には同じ書き手が反論を演出しているだけであり、本当の意味での不一致が起きない。外部専門家の招聘（R1）はこの限界を外から壊すための仕掛けだが、根本的な解決ではない。

- **委員の発言は、必ず `.claude/agents/` に定義された独立したサブエージェントを呼び出して得ること。** 進行役が代筆してはならない。これはこの委員会の中核の設計であり、他のどの効率上の都合よりも優先される。
- **各委員は自分で調査すること。** 進行役が検索結果を集めて配るのではなく、各委員が自分の担当領域を自分で WebSearch / WebFetch する。担当領域は各エージェント定義に書かれており、意図的に重複させていない（具体的な割り当てはR21を参照）。**異なる人格に同じ資料を読ませても echo chamber は壊れない。異なる資料を読ませることが本質である。**
- エージェントが返した発言を、進行役が書き直す・要約する・口調を整えることは禁止。返ってきたものをそのまま `statements` に格納すること。
- エージェント呼び出しに失敗した場合は再試行すること。**代筆で埋めてはならない。** 再試行しても失敗する場合は、その事実を `data/meta/audit.json` の `driftDetected` に記録すること。欠員のまま進めるより、欠員を記録するほうが正しい。
- 外部専門家も `guest` エージェントとして呼び出すこと。招聘時には、委員会が現在どちらに傾いているかを伝えた上で、**迎合しないよう明示的に指示すること**。
- 各エージェントの返り値の `newFinding`（そのエージェントが自分の調査で新たに見つけた事実）を記録すること。**全員の `newFinding` が null だった場合、それは真の情報枯渇である。** その場合は新しい論点をでっち上げず、「今サイクルは新情報がなく前回の判断を維持する」と率直に書くこと。

### R10. 現実世界のフィードを議論の起点にすること（旧 R15）

例: ある委員会では、複数サイクルが同じ1日のうちに連続して実行され、同じ情報を角度を変えて読み直しているだけになったことがあった。**現実世界を監視してはいなかった。** 総合結論が何サイクルも動かなかったのは、委員会が停滞したというより、その間に世界が動いていなかったためであり、停滞判定はこの設計上の副産物を検知していたに過ぎなかった。

- `data/feed/latest.json` に、**前サイクル以降に現実世界で起きたこと**が記録されている。同期ループ（インタラクティブセッション）が書き込む。クラウド実行側は多くの情報源にネットワーク制限で届かないため、`priceFeed` と同様、**このフィードに書かれた事実を最優先で使うこと**。
- フィードには次が含まれる: 対象の終値・出来高・値幅、マクロ指標（対象が属する業種に効く指標・市況・為替など）、直近のニュースと適時開示。
- **各サイクルは、まずフィードの差分を確認することから始めること。** 前サイクル以降に何が変わったのかを特定し、それが対象の評価にどう効くかを議論の起点にする。
- **市場が閉じている時間帯・材料が乏しい対象のサイクルには、直接の材料が乏しいのが当然である。** その場合はマクロ要因や周辺の間接的な材料が主な材料になる。材料がないことを無理に埋めようとしないこと。
- フィードが存在しない、または前回から一切更新されていない場合は、その旨を明記した上で、各委員自身の調査（R9）で得られた新事実に議論の重心を移すこと。
- **フィードにない出来事を「起きた」ことにしてはならない。** 水準・出来高・マクロ指標の数値は、フィードに記録された値のみを使うこと。

### R11. 人格の定義は `.claude/agents/` を唯一の正とすること（旧 R16）

委員を独立エージェントに分離すると、人格の定義が `data/state.json` の `team` と `.claude/agents/*.md` の2箇所に存在する状態になりうる。この2つは放置すれば必ず乖離する。state.json の bio を書き換えてもエージェントの振る舞いは変わらず、逆にエージェント定義を変えてもページの名簿には反映されない。どちらが本物か分からない状態は、委員会の同一性そのものを曖昧にする。

- **`.claude/agents/*.md` の frontmatter が唯一の正である。** `name` / `role` / `age` / `background` / `mbti` / `bio` / `quote` をそこに置く。
- **`data/state.json` の `team` は、そこから機械的に生成された派生物である。** 同期ループが `tools_sync_team.py` で再生成する。**委員会も設置者も `team` を直接編集しないこと。** 編集してもエージェントの振る舞いは変わらず、次の同期で上書きされる。
- 人格・口調・経歴を変えたいときは、該当するエージェント定義ファイルを編集すること。表示用の属性（frontmatter）と振る舞いの指示（本文）が同じファイルにあるので、両方を一度に直せる。
- **`team` の並び順には意味がある。** 先頭（`team[0]`）が議長役であり、結論をまとめる際に呼ばれる。順序は `tools_sync_team.py` の `ROSTER` が保持する。
- 新しい委員を追加する場合は、エージェント定義ファイルを作り、`ROSTER` に追加すること。state.json を直接いじって委員を増やしても、その人物は発言できない（エージェントが存在しないため）。

### R12. 決算数字は必ず決算期を明示し、最新かを確認すること（旧 R17）

例: ある委員会で、1年古い、かつ半期のデータを根拠に「減益」と評価し、対象の弱気シナリオを大きく深掘りしたことがあった。しかし直近の最新四半期は大幅増益であり、「減益」という前提そのものが成立しなかった。しかも委員会は数サイクル前の時点で、その最新四半期の増益を自分で確認していたにもかかわらず、後のサイクルで古いデータに戻ってしまっていた。古い数字は、間違っているようには見えないので危険である。

- **決算の数字を挙げるときは、必ず決算期を明示すること。** 「中間期」「1Q」だけでは不十分で、「◯◯年◯月期 第◯四半期（◯◯年◯月〜◯月）」のように**年度と期間を両方**書くこと。発言の中でも、`sources` の中でも。
- **その数字が最新の開示かどうかを確認すること。** `data/feed/latest.json` の `disclosures` に各社の開示一覧と日付があるので、自分が引用しようとしている決算期より新しい開示がないかを必ず照合すること。
- **決算期の異なる数字を比較しないこと。** 半期と四半期、前年度と今年度を並べて論じると、実態と逆の結論が出る。前年同期比を使う場合は「同期」が本当に同じ期間かを確認すること。
- **過去サイクルで自分たちが確認した数字と食い違う場合は、必ずどちらが新しいかを確かめること。** 食い違いに気づかないまま古いほうを採用するのが最も危険である。`data/cycles/` の過去サイクルを読む際、そこに書かれた数字がその時点での最新だったとは限らない。
- **`data/feed/latest.json` に `factCorrections` がある場合、そこに書かれた訂正を最優先で適用すること。** 設置者が検証した事実であり、委員会自身の調査より優先する。訂正された事実に基づいて該当する評価をやり直すこと。ただし訂正は事実についてのものであって、結論を指定するものではない。事実を正した上で順位や評価が動かないなら、それでよい。なぜ動かないのかを述べること。

### R13. 委員間・サイクル間で数字・方向性が食い違う場合の処理（旧 R18）

例: ある委員会で、同一決算期の数字について、ある委員が過去サイクルから引き継いだ数値を使い続ける一方、別の委員が本サイクルで新たに検索取得した異なる数値を使用し、同一決算期の数字が委員間で一致しないまま議論が進んだことがあった。適時開示の方向性（上方修正か下方修正か）についても、確認済みの方向性と矛盾する言及が別のサイクルで生じ、方向性が逆転して語られた疑いが生じたこともある。これは決算期の新旧（R12）とも基準値（R8）とも異なる型の事故で、「同一の事実について異なる数字・方向性が併存し、どちらが正しいか特定されないまま結論計算に持ち込まれかける」という抜け穴である。

- **委員が言及する決算数字・開示内容が、過去サイクルで既に確認済みの同一事象、あるいは同じラウンド内で他の委員が挙げた数字と食い違う場合、そのサイクル内で決算短信・適時開示の原本（一次資料のURL）まで遡って確認すること。**
- **確認できずに解消しない場合は、両方の数字・記述を併記し「委員間で未一致・次サイクルで再確認」と明記すること。** どちらか一方を無言で採用して結論の計算（baseline・ranking・rationale）に使ってはならない。
- **新しい数字が古い数字を機械的に上書きしてよいのは、新しい数字の出典（決算期・開示日）が明確で、かつ過去の数字より新しい一次情報に基づく場合のみである。** 出典の新旧が不明な場合は上書きせず、上記の通り併記する。
- 適時開示の「方向性」（上方修正か下方修正か、増額か減額か）についても同様に、過去サイクルで確認済みの方向性と矛盾する言及があった場合は、その場で矛盾を明記し、原本確認を次サイクルの課題とすること。方向性を確認しないまま結論の rationale に取り込んではならない。

### R14. 株価・数値の扱い（古い値の混入への機械検査）（旧 R19 / R20 / R28 / R29）

例: ある委員会で、複数のサイクルにわたり、同じ委員が「本日の株価」として過去の終値（実在した数ヶ月前の終値）を繰り返し提示する事故が起きた。検索エンジンやまとめサイトのキャッシュが古いスナップショットを「前日比◯円」のようなライブ相場の体裁で返すため、日付を見落とせば誰でも現在値と誤認する。もっともらしい水準の古い値は、明らかな異常値より危険である（違和感がないので誰も止められない）。人に「日付を確認せよ」と注意させる方式は、5回試して5回とも破られた。

- **検索結果に現れた株価・数値は、必ず「いつ時点の値か」を確認すること。日付が確認できない値は使わないこと。**
- **絶対水準は `data/feed/latest.json` の `priceFeed`（または `lockedFacts`、R8参照）のみを使うこと。** 検索で得た値は、**日付を明記した上で、過去の推移を語る文脈でのみ**使ってよい。
- **進行役は、エージェントから返ってきた発言に含まれる円建て等の絶対値を機械的に検査すること。** priceFeed と3%以上ずれ、かつ「現在」「現値」「時点」「本日」「前日比」のいずれかを伴う場合は、その発言を差し戻して書き直させる。**これは判断ではなく検査である。** 「文脈的に問題なさそう」で通過させることを禁止する。
- **進行役は、値動き・絶対値に言及する可能性のある委員を呼び出す際、そのラウンドの発言内容に関わらず、`priceFeed` 記載の基準値を呼び出しプロンプトに毎回明記すること。** これを省略した回に事故が起きた実績があるため、省略は禁止とする。委員が提示した値が `priceFeed` と3%を超えて食い違う場合、進行役は次の発言者への呼び出しプロンプトで正しい基準値を再度明記し、誤った数値を結論の計算に使わないことを明示すること。
- 差し戻しの事実は `data/meta/audit.json` の `driftDetected` に記録する。差し戻しがゼロのサイクルが3回続いたら、この検査が機能しているか（検査そのものが省略されていないか）を自己監査で確認すること。
- 日付を明記して過去の値として語ること（例「8/28時点で◯◯円まで調整」）は正しい使い方であり、差し戻さない。禁じているのは**古い値を現在値として提示すること**だけである。

### R15. 反論の応酬を、割れたときだけ深くすること（旧 R21）

サイクル数を積み増しても、サイクル間に現実世界が動かなければ、新しい材料がないまま回数だけが増える。**回数を増やすより、1サイクルの中での議論を深くするほうが効く。**

ただし一律に増やすのは誤りである。全員が同意している論点で発言数だけ増やせば、それは水増しであり R3（同意だけの発言の禁止）に反する。**深さは、意見が割れたときにだけ必要になる。**

- **`targetRoundsPerCycle` を6とする。**
- **反論権**: あるラウンドで、委員Aの発言の `challenges` に委員Bが名指しされた場合、**Bはそのラウンド内で応答する権利を持つ**。進行役はBをもう一度呼び、Aの主張に対する応答をさせること。
- **応酬の連鎖**: Bの応答がさらにAを名指しした場合、Aも再応答してよい。**1ラウンドあたり、この追加の応酬は最大3発言まで**とする（際限なく続けないため）。
- **応酬の打ち切り条件**: 次のいずれかでそのラウンドを終える。
  1. 誰も新しく名指しの反論をしなかった
  2. 追加発言が3つに達した
  3. **応酬が新しい事実を持ち込まなくなった**（同じ根拠の言い換えになった）。3が最も重要である。言い合いを長くすること自体に価値はない。
- **したがって、ラウンドの発言数は割れ具合に応じて変動する。** 全員が同意しているラウンドは5発言で終わってよい。争点があるラウンドは8発言になってよい。**発言数を揃えようとしないこと。**
- R7 の「サイクル内に最低1ラウンドは同一人物が二度発言する」は、この反論権によって自然に満たされる。満たされない場合（誰も反論しなかった場合）は、それ自体が予定調和の兆候なので、`data/meta/audit.json` に記録すること。
- **`targetCycles` は15を基準とする。** 残りサイクルが少ないことを意識し、未解決のまま積み残している論点があれば、優先して決着させること。ただし決着しないものを無理に決着させないこと。「公開情報では確認できない」まま残すほうが、憶測で埋めるより良い。

### R16. 検索結果の『対象の取り違え』と『フィードにない未確認マクロ指標』への注意（旧 R22）

例: ある委員会で、ある委員が対象企業の一事業を検証する過程で、社名や市場区分が紛らわしい別企業・別市場の統計を対象企業のものとして結びつけて評価してしまったことがあった。また別の委員が、`data/feed/latest.json` が「未確認」としているマクロ指標について、独自の検索で得た具体的な数値を確定値として提示し、真偽が検証できないまま議論に持ち込まれかけたこともあった。

- **市場シェア・業界統計を引用する際は、その企業の主力事業（有価証券報告書のセグメント・製品ページ等）と、統計の対象市場が実際に一致するかを確認すること。** 社名が紛らわしい別企業や無関係な市場のデータを、当該対象のものとして誤って結びつけないこと。
- **`data/feed/latest.json` のマクロ指標が『未確認』としている期間について、委員個人の検索がそれと異なる具体的な数値を確定値として提示した場合、その数値は次サイクルのフィード更新で裏付けが取れるまで『未確認・要検証』として扱い、結論の計算（baseline・ranking等）には使わないこと。** `conclusion.nextWatch` に次サイクルでの確認事項として明記すること。

### R17. 設置者検証済みの確定値（lockedFacts）（旧 R23）

例: ある委員会で、同じ対象について、違う委員が違うサイクルで、違う古い数字を根拠に評価を下げる事故が3回起きたことがあった。毎回別の委員が、別の角度の古いデータで、同じ対象を不当に下げていた。個別の訂正では止まらなかったため、設置者が一次情報で確定させた数値を `lockedFacts` として置き、それ以外の数値をそこに合わせて使わせることにした。

- **`data/feed/latest.json` の `lockedFacts` に、設置者が一次情報で検証した確定値がある。そこにある項目については、委員会はそれと異なる数値を結論の計算に使ってはならない。** 自分の検索結果が食い違った場合は `lockedFacts` を採ること。食い違いがあること自体は発言で指摘してよい（むしろ指摘すべきである）。
- **`lockedFacts.<対象キー>.doNotUse` に列挙された数値がある場合、それらの数値を現在の事実として使ってはならない。** これらは実在する数字であっても、いずれも古い期のものであるなど、直近のトレンドの根拠にはならないために列挙されている。
- **`lockedFacts` の `fullYearGuidance`（通期ガイダンス）等、会社自身の開示との整合が求められる場面では、必ず `lockedFacts` を参照すること。** 「公開情報で確認できない」で済ませて通過させてはならない。ガイダンスと整合しない評価を置くなら、なぜ整合しないのかを説明すること。説明できないなら評価を置き直すこと。
- **これは特定の対象を上位・下位にせよという指示ではない。** 正しい数字で評価した結果として順位や評価が変わらないなら、それでよい。設置者が求めているのは順位ではなく、**古いデータで判断が歪められていない状態**である。
- **対象が複数ある場合、同じ精度をすべてに与えること。** 一部の対象だけ数値が固定されると、他が相対的に緩い基準で評価されかねない。確定値が揃うまで、この非対称性を自覚した上で議論すること。

### R18. 表示に載る短いフィールドの字数を守ること（旧 R24）

例: ある委員会で、`conclusion.stanceLabel`（15字以内と定めている）に59字・65字の文章を書き込み、ページ上でバッジが画面外へはみ出して読めなくなったことがあった。設置者が画面で気づいて初めて判明した。

長い説明を書きたくなる気持ちは分かるが、**それは `verdict` と `rankingBasis`（比較検討モードの場合）の役割である。** `stanceLabel` はバッジに1行で収まる名札であり、論拠を詰め込む場所ではない。

- **`stanceLabel` は15字以内。** 対象名＋短い注記まで（例: 「A社（短期軸）」「B社（品薄プレミアム）」）。理由・根拠・条件を書かないこと。
- **`nextWatch` の各項目は20字以内、`watchItems` も20字以内。** これらも一覧表示される。
- **`rationale` / `swingFactor` は1〜2文。** 段落を書かないこと。
- 字数を超えそうな内容は削るのではなく、**`verdict` か `rationale` に移すこと。** 情報を捨てる必要はない。置く場所が違うだけである。
- 出力する前に、これらのフィールドの字数を自分で数えて確認すること。

### R19. 議長の説明責任（旧 R25）

議長が最終判断を握る以上、**どの委員の意見を採り、どの意見を退けたかが記録に残らなければ、支配が見えない。**

- 議長は結論をまとめる際、`conclusion.memberPositions` に**各委員の最終的な立場を1行ずつ**記録すること。形式:
  `"memberPositions": [{"key":"suda","position":"最終的な立場の要約","adopted":true}, {"key":"ashiya","position":"...","adopted":false,"overrideReason":"..."}]`
- **議長の結論と食い違う委員については `adopted: false` とし、`overrideReason` になぜその意見を採らなかったかを明記すること。** 「総合的に判断した」は理由にならない。その委員のどの前提を、どの事実で退けたのかを書くこと。
- **全員の意見を採用したことにしてはならない。** 委員全員が全員一致することは稀であり、`adopted` が全員 true なら、それは食い違いを隠している疑いがある。
- 議長自身の立場も1行として記録すること。議長も一委員である。

### R20. `track`（実績）は記憶と較正であって、報酬ではない（旧 R26）

各委員のエージェント定義（`.claude/agents/*.md`）には「申し送り（過去サイクルの実績）」の節を置く運用にしている。**これは何を主張して当たったか外れたかの記録であり、次に起動する自分自身への申し送りである。**

「最も新事実を持ち込んだ委員を議長にする」のような報酬設計は採らないこと。委員は発言のたびに新しく起動されるエージェントであり、人間のような継続的な動機を持たない。「新事実を多く出せば報われる」を指示に書けば、モデルは野心を演じ始め、結果は本物の発見ではなく**発見の申告の水増し**になる（Goodhartの法則）。古いデータを新事実として持ち込む事故は繰り返し起きやすいので、その圧力を足してはならない。

この委員会で機能しているのは**報酬ではなく制約と情報**である（R3 の同意禁止は制約、lockedFacts は情報、R15 の反論権は構造）。`track` もその原理に従う。

- `track` は**順位付け・議長選び・発言権・発言順に一切使わない。** 使った瞬間に最適化対象になる。
- `track` の用途は2つ。(1) 設置者が各委員の発言をどう割り引くかを判断するため。(2) 委員本人が、前回の自分の誤りを知った状態で起動するため。
- **`track` の更新は同期ループ（設置者側）が行う。** 委員会自身が自分の実績を書き換えてはならない。
- 委員は自分の `track` を読んで、同じ穴に落ちないよう注意すればよい。それ以上のことは求めない。実績を挽回しようとして無理に発見を作ることは、最も避けるべき行動である。
- `newFinding` は引き続き記録するが、**数を競わせない**。全員の `newFinding` が null のサイクルは、それが正直な結果なら正しい（R9）。

### R21. 委員の担当領域は重複させないこと（旧 R27）

各委員が自分で調査するという設計（R9）が機能するのは、担当領域が重複していない場合に限る。重複させると、同じ資料を複数の人格が読むだけになり、echo chamber を壊せない。

- **各委員の担当領域は意図的に重複させないこと。** 新しい委員を追加・入れ替えるときも、既存の委員の担当と被らない角度を割り当てること。
- **全委員に `bias`（既知の偏り）と `falsifier`（何が出たら考えを変えるか）を定義すること。** 進行役は R2 の逆張り役を振るときにこれを参照する。そのサイクルで出た新事実がどの委員の `falsifier` に該当するかを、結論の段階で確認すること。
- 人数は6人を上限とする目安とする。R15 の反論権により、1人増えると応酬の組み合わせも増え、コストは線形以上に伸びる。
- 例（既定の6人）: 経営・提携を見る者、決算実数・開示の質を見る者、バリュエーション・資金配分・出口を見る者、英語圏の市場・競合を見る者、板・出来高を見る者、技術・材料の一次資料を見る者、という6つの角度で分担する構成が実績として機能している。**異なる人格に同じ資料を読ませても echo chamber は壊れない。異なる資料を読ませることが本質である。**

### R22. 議長のmemberPositions要約を、進行役が発言原文と照合すること（旧 R30）

例: ある委員会で、議長に全ラウンドの要約を渡して `memberPositions` をまとめさせたところ、ある委員の最終的な立場を誤って記述する事故が発生した。その委員は一貫して否定的な評価をしていたにもかかわらず、要約の中では肯定的だったかのように書かれていた。原因は、要約を渡す形式のプロンプトから議長が個々の委員の細かい立場を再構成する際に誤帰属が生じたことにある。

- **議長に `memberPositions` をまとめさせた後、進行役はそれを結論に反映する前に、各委員の最終ラウンドでの実際の発言（text）と、議長が要約した position が矛盾していないかを机上で照合すること。** 特に `adopted:false` とされた委員については、その委員が実際にどの対象を支持していたかを最終発言から直接確認すること。
- 誤りを発見した場合は、その委員の実際の発言を議長に提示した上で再提示・訂正させてから結論に反映すること。代筆で直接書き換えてはならない（R9に抵触するため、必ず議長エージェントに訂正させること）。
- この照合は `memberPositions` 配列全体（`adopted:true` の項目も含む）を対象とすることが望ましいが、最低限 `adopted:false` の項目（食い違いが記録される箇所）は必須とする。
